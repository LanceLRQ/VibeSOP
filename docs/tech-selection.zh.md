# 技术选型指南

[English](tech-selection.md) | 中文

适用时机:仓库初始化完成,还没有代码,不知道从哪一步开始。本文给的是方法和截至 2026-10 的主流候选;各选型的版本请在动手前自行核实——选型内容的时效性远高于治理规则。

## 路径

需求 → 选型 → 脚手架 → 回到 `vibesop-init-deployment`。

需求先行是硬规则:平台没定,候选就不该出现。要做小程序,Web 框架再主流也不进候选;要做命令行工具,ORM 和 UI 库都不该被提起。

## 先问清楚的五件事

| 问题 | 为什么影响候选 |
|---|---|
| 跑在什么平台:Web、小程序、App、桌面、服务端 API、CLI | 第一道过滤器 |
| 谁在用、用得多重 | 内容站、内部工具、付费产品,对成熟度的要求不同 |
| 团队已经会什么 | 团队熟悉的技术胜过略优的技术 |
| 只做国内还是面向全球 | 支付、合规、网络可达性都会改名单 |
| 本次接受前沿路线吗 | 默认不接受;接受后,候选里才会出现前沿选项 |

## 按场景的主流候选(截至 2026-10)

「默认候选」按主流优先:生态成熟、部署广泛、资料和招人容易。标注「前沿」的是正在成为主流但尚未完全落地的选择,采用前先评估团队的承受力。

### Web 前端

| 候选 | 适用 | 备注 |
|---|---|---|
| React + Next.js | 默认 | 生态最大,App Router 已稳定 |
| Vue 3 + Nuxt | 团队会 Vue | 国内生态好,Nuxt 4 已发布 |
| Svelte 5 + SvelteKit | 追求运行时轻 | 生态较小,属次主流 |

样式默认 Tailwind CSS,语言全场景默认 TypeScript。

### 小程序

| 候选 | 适用 | 备注 |
|---|---|---|
| 微信原生 | 只做微信一个端 | 无跨端折损 |
| Taro 4 | 团队会 React | 编译到微信/支付宝/抖音等各小程序端及 H5 |
| uni-app / uni-app x | 团队会 Vue | 多端覆盖广;uni-app x 走原生编译路线,仍偏新 |

需要鸿蒙(HarmonyOS NEXT)端时,先确认所选框架当期的适配状态——这是 2026 年仍在快速变化的一块,不要凭旧资料承诺。

### 移动 App

| 候选 | 适用 | 备注 |
|---|---|---|
| Expo(React Native) | 团队有 Web/JS 背景 | 2026 年 React Native 的事实标准入口,新架构默认启用 |
| Flutter | UI 密集、要求多端一致 | Impeller 渲染器在双端已默认 |
| 原生 Kotlin / Swift | 平台能力要求高 | 双端两套代码,成本高,按需选择 |

### 桌面

| 候选 | 适用 | 备注 |
|---|---|---|
| Electron | 默认 | 生态最成熟,代价是安装体积 |
| Tauri 2 | 在意体积与内存 | Rust 内核,前端自选 |

### 服务端

| 候选 | 适用 | 备注 |
|---|---|---|
| TypeScript:NestJS / Fastify / Hono | 与前端同语言 | NestJS 结构全、适合规模大的项目;Hono 轻、适合边缘部署。认证用 better-auth,数据库层用 Drizzle 或 Prisma |
| Python:FastAPI | API 服务 | 异步、类型提示、文档自动生成 |
| Python:Django | 需要后台管理与 ORM 全家桶 | 成熟省事 |
| Go:标准库路由 + Gin | 高并发、部署简单 | 单二进制交付 |
| Java:Spring Boot 3 | 企业环境 | 事实标准 |

认证(TypeScript)补充:better-auth 是 2026 年新项目的默认选择;Auth.js(NextAuth)成熟、与 Next.js 结合最深;Lucia 已停止维护,只作学习参考。

数据库:PostgreSQL 是默认答案;MySQL 在国内生态仍然广泛;SQLite(含 libSQL)适合嵌入式与本地优先场景;MongoDB 只在数据天然是文档型时考虑。

## 前沿路线

「主流优先」是默认档位,不是上限。用户明确选择后可以走前沿路线,受三条规则约束。

先分清两层风险:

| 层 | 例子 | 采用前沿的代价 |
|---|---|---|
| 工具链层 | linter、formatter、构建器、更快的编译器 | 低:锁在开发依赖与配置里,退回只改配置,业务代码不动 |
| 运行时/依赖层 | 框架、ORM、认证库 | 高:熔进业务代码,退路是一次真迁移 |

准入条件,满足其一才给前沿候选:绿地项目,没有迁移成本;或候选属于工具链层,退路便宜;或用户明确接受迁移成本,且候选带清楚的退路。每个前沿候选写清三件事:它解决了主流方案的什么问题、退路是什么、验证状态(谁验证过、什么规模)。

有一类证据要正确使用:经 CI 对全组合做过安装、类型检查、测试、构建验证的组合清单,证明的是这些新东西能一起工作,不是它们在生产环境里耐用——出生证明不是体检报告。

存量项目不适用前沿路线:已经在跑的项目保持原有技术栈,除非用户明确要求迁移,否则不做迁移、重写或升级的建议。前沿路线是给新项目的选项,不是给老项目的改造理由。

## 决策记录

选型结论是一份过程文档,不是聊完就散的对话:

1. 写成 `specs/` 下的一份选型决策(比较过程长则放 `research/`),登记进文档索引。
2. 记录四个要素:需求要点、候选与取舍理由、选定项及其版本、决策日期。
3. 选定后,技术栈即可作为用户陈述写入 `AGENTS.md`;脚手架产出 manifest 之后,后续会话会把它作为事实探测到。

`vibesop-init-project` 在新项目入口的收尾报告中会给出这条路径的纲要,本文是它的完整版。

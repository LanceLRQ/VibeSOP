# vibesop-init-deployment:部署环境

[English](vibesop-init-deployment.md) | 中文

`vibesop-init-deployment` 为网站项目生成基于 Docker 的各套环境与管理脚本。流程原文是 [`skills/vibesop-init-deployment/SKILL.md`](../skills/vibesop-init-deployment/SKILL.md),本文面向使用者。

## 适用与不适用

适用:需要搭建或整理 Docker 环境的网站与 web 服务项目,语言、框架、服务数量不限。已有部署结构的项目采取补齐方式:先列现状与差异,由用户确定修改范围,不拆重建。

不适用:Kubernetes、Serverless、纯静态托管(如 Vercel、OSS 静态站),遇到时 skill 会明确说明不在范围内。文档分区与 AI 指令文件属于 `vibesop-init-project`。

## 服务清单

一切从服务清单开始:每个可独立运行的进程(后端、前端、管理后台、工具进程),连同构建方式、监听端口、数据目录与是否有状态。清单以表格形式交给用户确认——清单错了,后面全错。探测到的值只作为推荐默认值,仍逐项询问确认。

## 环境

| 环境 | 默认 | 职责 |
|---|---|---|
| 本地开发 | 启用 | 源码挂载与热重载,数据落在本地被忽略的目录 |
| 生产 | 启用 | 运行镜像,应用与数据库的生命周期分离 |
| 内网 | 可选 | 局域网测试或预发机,结构与生产相同 |
| 灰度 | 可选 | 与生产同机运行,切分流量验证新版本 |

选择灰度时,必须确认共享生产数据库还是使用独立数据库;共享时不生成任何会破坏旧版本的迁移指引。构建期变量(`NEXT_PUBLIC_*`、`VITE_*` 等)与后台任务(定时任务、队列消费者)在灰度环境中是重点风险,逐一确认。

## 发布路线

第一个问题决定方向:

| 路线 | 产出 |
|---|---|
| 私有项目(默认) | 各环境 compose 文件与 `dev.sh` / `prod.sh` 管理脚本;镜像推送私有仓库(如阿里云 ACR),或在服务器上直接构建 |
| 开源项目 | Docker Hub 公开镜像、由 tag 触发的发布流水线、用户一行命令即可运行的单文件安装脚本 |

治理记录标注开源的仓库,推荐开源路线;无论哪种路线,本地开发环境都会生成。

## 其他关键决策

- 部署账号:root、sudo 用户或 docker 组普通用户,三种都支持;它与容器内运行用户共同决定数据目录是否需要 chown、命令示例是否带 sudo。
- 反向代理:对外暴露的 HTTP 服务只有一个时,不内置 Nginx 并说明理由;两个及以上时询问用户并解释取舍。
- 镜像仓库:阿里云 ACR(未配置时逐步引导)、在服务器上克隆仓库构建、`docker save/load` 手动搬运,三者选一。

## 验证与交付

生成后逐项验证:每个脚本通过 `bash -n` 检查;每个 compose 文件通过 `docker compose config -q`;数据目录与密钥文件命中忽略规则;`*.example` 文件不被忽略规则误伤;产物中没有残留的模板占位符;`git status` 中没有暂存项。

交付时给出:生成文件清单、每个环境的命令速查,以及必须由用户亲自完成的事项——填写 `.env`、配置镜像仓库凭证、在服务器上 chown 数据目录、配置反向代理与域名。

## 红线

- 没问过的值不写入磁盘
- 密码、密钥、token 只进被忽略的文件,入库的只有 `*.example` 模板
- 不执行 `docker push`,不登录服务器,不触碰线上环境,不执行 git 提交或推送;生成文件即止
- git 只读使用,所有改动留在工作区供用户审阅

## 常见错误

这些错误在真实项目中发生过,skill 的规则围绕它们设计:

| 错误 | 后果 |
|---|---|
| 一次性抛出全部问题 | 用户缺乏上下文,难以决策 |
| 直接采用探测到的端口 | 与服务器上其他项目冲突,端口始终逐个询问 |
| 单服务项目加一层 Nginx | 多一个需要维护的组件 |
| 只推送 latest | 出问题无法回滚;版本标签与 latest 同时推送 |
| ARM 机器构建、x86 服务器运行 | exec format error;构建时显式传 `--platform` |
| 灰度与生产同时运行后台任务 | 消息被消费两次、定时任务跑两遍;灰度默认停用后台任务 |
